# Phrase VAE — a second, more experimental companion

Prepared 2026-09-12, same machine as `bench/amt`. Same goal (a live AI duet
partner) and same synthetic-piano-melody setup, but a completely different
model family, to see what a different tradeoff looks like. Self-contained:
no dependency on `bench/amt` or the `anticipation` package, only
`torch`, `musicpy`, and `mido`.

## The idea

`bench/amt` is autoregressive: generate one token at a time, conditioned on
everything before it. That's *why* most of that bench is spent hiding
inference latency behind a lookahead/commit buffer — token-by-token
generation is inherently slow relative to real time.

A VAE is a completely different shape: encode a short phrase to a point in
a small latent space, decode a (possibly different) phrase from a nearby
point, in one forward pass. No loop, no scheduling problem — but also no
notion of "continue this in real time." So this companion doesn't play
*simultaneously* with the human the way `bench/amt`'s does; it plays
**call-and-response**: it listens to an 8-note phrase, then answers with a
decoded one, once the human's already finished playing it.

`phrase_vae.py` is a small GRU encoder/decoder (latent dim 8, hidden dim 64)
operating on scale-degree sequences (0-7), not absolute MIDI pitch, so one
checkpoint works in any key. It's trained from scratch, on synthetic
phrases generated by the same random-walk-with-cadence shape as
`bench/amt/melody.py`'s live performer, every time you run the script —
there's no saved checkpoint to keep in sync with anything.

## Run

```bash
pip install torch musicpy mido soundfile numpy
python live_duet_vae.py --notes 32 --bpm 80 --temperature 1.5
# writes ../../output/live_duet_vae.{mid,wav}
```

Flags: `--bpm`, `--key`/`--mode`, `--notes` (melody length), `--seed`
(melody), `--train-seed` (VAE training data), `--outdir`, and
`--temperature` — the latent sampling temperature. `1.0` is standard VAE
sampling (a fairly literal echo of the input phrase's contour); higher
pushes the decoder further from the encoded phrase into more of what it's
learned about phrase shapes in general, i.e. more "experimental," less
recognizably a response to what was just played. `0.0` decodes the mean
`mu` directly — closest to a literal reconstruction of the input phrase.

## Findings

- **Training took ~20s on CPU for the default 60 epochs** (4000 synthetic
  phrases, batch 64) — not the "couple of seconds" a VAE this size ought
  to take; a GRU decoder unrolled 8 steps per example has enough fixed
  per-step Python/kernel-launch overhead that wall time is roughly linear
  in epoch count regardless of the model's tiny size (~0.35s/epoch
  measured). At 60 epochs, token reconstruction accuracy was ~73% (200
  epochs gets to ~87%, at ~70s total) — a real quality/setup-time knob if
  this ever needs a snappier "soundcheck."
- **Decoding a response is ~1-5ms.** This is the actual point of the
  comparison: no lookahead buffer, no commit windows, no underrun logging,
  because there's no autoregressive loop to race against the playhead.
  `bench/amt`'s entire scheduling apparatus (lookahead/commit/listen-first,
  retries, per-voice monophony bookkeeping) is solving a problem this model
  doesn't have — the cost shows up as reduced expressiveness instead (fixed
  8-note phrases, no rhythm modeling, much smaller training signal).
- **It genuinely is more "experimental."** At `--temperature 1.5`, the
  decoded phrase's degree sequence resembles the input's general shape
  (starts low, similar range) but reliably diverges in the details — e.g.
  input `[1,0,2,3,4,4,3,0]` decoded to `[1,0,1,2,3,5,4,0]` in one run.
  This is a genuinely different character from `bench/amt`'s companion,
  which is trying to sound like a plausible continuation of a real
  multi-track song; this one sounds more like a smeared, dreamy paraphrase
  of what it just heard. Whether that's "better" depends entirely on what
  the demo wants — it's the deliberate tradeoff of a phrase autoencoder vs.
  a language-model-style continuation.
- **No rhythm modeling at all.** The companion's note durations are
  borrowed directly from the human phrase that triggered the response
  (same inter-onset gaps, transposed in time) — the VAE only ever decided
  *pitch* degrees. A real version of this would need duration in the
  latent representation too (e.g. a second output head, or interleaving
  duration bins into the token sequence the way `bench/amt` does).
- **Turn-taking, not togetherness.** Because responses only fire once a
  full 8-note phrase has been revealed, the companion is silent while the
  human plays and vice versa (mostly) — a call-and-response duet, not a
  simultaneous one. That's a design choice made because it's the natural
  fit for a fixed-length phrase model, not something imposed on it; forcing
  it to play *with* the human would need a different mechanism (e.g.
  overlapping windows, or a running latent state) and is a real next step
  if this direction gets pursued further.

## Next steps if this becomes a real companion mode

- Model duration alongside pitch (the single biggest quality gap vs.
  `bench/amt`'s output).
- A "response fires while the human keeps playing" variant — encode a
  sliding window instead of waiting for a full non-overlapping phrase, so
  it can layer under the human rather than only answer after them.
- Train on real melodic corpora (even a small one) instead of a synthetic
  random walk, so the response space has actual musical structure to draw
  on rather than an artifact of the training-data generator's own biases.
