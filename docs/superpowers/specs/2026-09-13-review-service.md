Date: 2026-09-13. Scope: `services/amt/**`, `services/acestep/**`, the pod scripts, `relay/`, `bench/streammuse/**`, and the protocol as `src/engines/amtEngine.ts` uses it. Read-only review; no code changed. Line numbers are from `origin/main` at `025a2f0`.

## 1. The generation loop

### What the model is asked

Per cue, `Session.generate_plan` (`services/amt/server.py:241-357`) does, in order:

1. `plan_window(now, span=commit_beats, lookahead)` -> `[now+2, now+4)` at the client's lookahead 2 / commit 2 (`arrangement.py:6-13`, `amtEngine.ts:19-20`).
2. `performance.observe_through(now)` extends still-held notes to the cue (`performance_history.py:895`), `prune_context` drops tokens older than 16 beats (`server.py:77, 208-231`).
3. The brain decides `chord` and `section` (`server.py:262-264`).
4. Gates: idle form or no instruments -> empty plan; no human notes or window end inside `listen_beats` (8) -> empty plan (`server.py:265-285`).
5. `start_beat = max(target, committed_horizon, listen_beats)`, `end_beat = max(commit_end, start + lookahead)` (`server.py:288-292`). With lookahead == commit == 2 the generated span equals the committed span: nothing is over-generated and discarded by windowing. The docstring at `server.py:290-291` ("anything past the commit point is discarded and rewritten next bar") describes the old 4/2 setting and is false for the deployed client.
6. `cached_generate` (`cached.py:780-828`): prompt = `[AUTOREGRESS] + last 1017 tokens` of the human+committed history, time-rebased; loop samples (time, dur, note) triples until a time token reaches `end`, with `future_logits` forbidding time < current, `_instr_mask_logits` dropping the melody instrument entirely (`accomp_only=True`, `amt.py:77-98`) and adding `accomp_bias` 2.0 to the chosen GM programs, `nucleus(top_p)` and temperature division. Deadline `0.8 * window_s` (`server.py:71, 303`).
7. Filter to `generation_instrs`, filter to `[start_tick, commit_end_tick)` (`server.py:320-326`).
8. `Arranger.constrain` -> `shape_notes` per instrument (`arrangement.py:201-221, 16-67`): grid snap (0.5 beat, 0.25 above creativity 0.65), duration quantise, chord-tone / scale-tone pitch snapping within +-6 semitones, a minimum onset gap (2 / 1 / 0.5 beats by amount), then a second gap pass in `constrain` (2 / 1 / 0.25 beats).
9. `AccompanimentCommitter.commit` (`bench/amt/live_duet.py:188-216`): per instrument, drops same-onset notes, trims the previous note's tail, appends to the token history.
10. `Arranger.events` maps GM program -> `keys|bass|lead` (`arrangement.py:174-180, 223-230`).

### What each step assumes and throws away

- The model is run in plain autoregressive mode. The prompt begins with `AUTOREGRESS` (`amt.py:126`, `cached.py:801`); no `ANTICIPATE` control tokens are ever built. The Anticipatory Music Transformer's defining capability (Thickstun et al. 2023: interleave *control* events that are known ahead of time, with the model trained to realise them ~5 s before they occur) is not used. This is defensible for the *human's* future, which is unknown, but two things are known ahead of time and are currently thrown into a post-hoc pitch filter instead of into the model: the brain's predicted chord for the window, and (at lookahead > commit) the model's own already-committed notes. The paper's intended live use is closer to: feed the predicted chord's bass/triad as anticipated control events at `window_start`, sample the accompaniment conditioned on them, and let the model voice-lead into a chord it knows is coming. Today the chord reaches the notes only through `shape_notes`'s +-6 semitone snap (`arrangement.py:56-61`), which is why the bench measured chord-tone share of 0.39 on the arpeggio, at chance (`bench/streammuse/REPORT.md`, table "Musical").
- The melody instrument is masked out (`accomp_only=True`). The ReaLJam/ReaLchords idea of jointly imagining the human's continuation is deliberately removed (`amt.py:83-91` explains why: with the mask off the model wrote 16 melody events and 0 accompaniment). Consequence: the model never reasons about what the singer will do in the window it writes for; it only continues its own part against a melody that stops at `now`. Combined with lookahead 2, the model always writes for a window whose melody it has never seen. This is the structural reason the harmony brain exists at all.
- Sampling: `sampling_for(creativity)` maps 0..0.8 to temperature 0.9..1.22 / top-p 0.85..0.962, then 0.8..1 to 1.5 / 1.0 (`brain.py:280-292`). CREATIVITY_BENCH.md concedes the model side is not the bottleneck ("today's mapping is already generating a wide spread"); the audible range of the knob comes from the filter's grid and gap (`arrangement.py:22-30, 56`), not from the sampler. Temperature 1.5 with top-p 1.0 on a 128M GPT-2 is close to unconditioned noise; the only reason it sounds acceptable is that step 8 snaps every pitch to the key.
- `min_interval_ticks` = a sixteenth (`server.py:311`) forces the clock forward after every event, so the loop terminates. Fine, but it also means the model cannot write a chord (two notes on one tick) even if it wanted to; polyphony is impossible by construction, and then `voice_chord` (`arrangement.py:70-100`) exists to add it back and is never called from `server.py` (see section 4).
- Discard arithmetic. `bench/amt/amt.py:27` measured the string ensemble at "7-80 notes per 4-beat window" raw. `shape_notes` at the client's amount 1.0 (`amtEngine.ts:81`, so `gap_beats` 0.5) and the second `constrain` pass (0.25) cap each instrument at 4 onsets per half bar; the committer then drops any same-tick duplicates. The recorded runs show 2-5 notes per 2-beat plan on the relay (`bench/streammuse/out/amt_*.log.json`: 2,3,4,2,4,4,3,2,5 and 5,5,5,4,2,4,5,4,3) and 2.4-3.3 notes per bar over 8 bars in `out/metrics.json` ("amt/melody_am": 26 notes / 8 bars). Against 7-80 generated per bar that is a discard rate between roughly 55% and 95%, dominated by the gap filter and the key snap, not by windowing. The exact live split (generated / in window / committed) is what the `log.info` at `server.py:334-340` reports and what nobody has looked at since the log was truncated.
- The `GENERATION_BUDGET` deadline is measured from `generate_duet` entry only. Queue time in `LatestPlanner` (`live_session.py:700`), the `copy.deepcopy` of the whole session per cue (`live_session.py:633-638`, including token history and every `PerformanceHistory` record), and the relay hop are outside the budget. See section 3.

### Compared with StreamMUSE and ReaLchords

StreamMUSE (bench/streammuse/REPORT.md) plays from beat 1, polyphonic, re-requested every 1-2 ticks; its weaknesses are exactly our strengths (no key conditioning, needs sub-200 ms RTT). ReaLchords / ReaLJam commit a chord per beat with lookahead/commit/listen and are trained (RL-finetuned) for online use. Our loop is a ReaLJam scheduler wrapped around an offline model that was never trained to be interrupted, with the harmony decided by a separate rule system. That is a reasonable hackathon compromise, but the honest statement is: the transformer contributes rhythm and contour; harmony comes from `harmony.py`/`predict.py` and the snap; density comes from `shape_notes`. Item 6 of the plan is the cheapest way to make the model contribute harmony.

## 2. Harmony brain

Pipeline per tick (`brain.py:366-406`): `MelodyHarmonizer.tick(tick - 0.125 s)` -> `Reading` (chord + half-bar pitch-class weights) -> `decide()` (four rules) -> `recent_chords` -> step the prediction forward once per downbeat between tick and window start -> `client_chord` override if fewer than four notes heard.

Principled parts:

- Coverage over a fading pitch-class window with a bass boost (`harmony.py:88-103, 118-123`) is a sensible emission model; it is a hand-rolled chord template matcher.
- A transition matrix fitted on 468k songs (`fit_transitions.py`, `data/transitions.json`) is the right prior for "what comes next".
- A Viterbi over the last four half bars (`predict.py:420-467`) is the right decoder for "which chord is the singer on".

Bench-fitted patches, in order of how much I would remove:

1. `rejected()` (`predict.py:578-602`): pattern-matches the band's own last six decisions and their HEARD/PREDICTED tags to stop the predictor pushing off a held chord twice. HARMONY_BENCH.md says plainly it exists for the `held-4-bars` scenario and "lifts the held scenario from 25% to 62%". In a proper HMM this is the self-transition probability plus accumulated evidence; there is no reason to track provenance tags.
2. `decide()`'s four rules with `READING_TRUST` 0.75 and `PREDICT_MIN_COVERAGE` 0.5 (`predict.py:605-641`). HARMONY_BENCH.md: these thresholds "never decide the bar-start number on these clips". They are untested by the only bench that exists.
3. Two predictors kept side by side (`PREDICTOR = 'table'`, `brain.py:265`) with two code paths in `decide_chord` and a third in `predict_ahead_hmm`. The docs disagree with the code: `services/amt/README.md` ("The default predictor (`PREDICTOR = 'hmm'`)") and HARMONY_BENCH.md ("brain.py uses it by default (PREDICTOR = 'hmm')") both say hmm; `brain.py:265` says table, per commit `024b78d`. The stated reason is "loses one bar on the live replay and 12 points on the minor loop", i.e. one scenario of four.
4. Stay probabilities 0.35 / 0.85, `EMISSION_ALPHA` 2, `ROOT_BONUS` 0.5 (`predict.py:278-291`) were all chosen on the same four synthetic 8-bar scenarios (32 bar decisions) that report the result. The alpha sweep table in HARMONY_BENCH.md is the training set.
5. `DETECTION_LATENCY_S = 0.125` (`brain.py:275`): the harmonizer is ticked 0.125 s behind the cue so a note that arrived with an onset inside the last 0.19 beats (at 90 bpm) is *ignored* (`harmony.py:97`, `age < 0 -> continue`) even though the client already sent it. The bench replays with the same constant (`bench_harmony.py:254, 281`), so the bench cannot tell whether it helps. It also does not do what the comment says: the client stamps the *onset* (`amtEngine.ts:248`), so the harmonizer is discarding real evidence, not correcting for late evidence.
6. `CLIENT_CHORD_MAX_NOTES` override (`brain.py:268, 404-405`): a compatibility shim; the deployed client sends `chord` in every `set` (`amtEngine.ts:328`) and the server ignores it after four notes. Drop the field on the client once the service is authoritative.
7. `MELODY_SWITCH_MARGIN` 0.15 / `MELODY_MIN_COVERAGE` 0.5 hysteresis in `harmonize_melody` (`harmony.py:155-158`): a second, independent stickiness mechanism on top of the HMM's stay probability. Two stickiness knobs that were tuned separately.

Clean formulation (one object, ~120 lines, replaces `harmonize_melody`, `Reading`, `decide`, `rejected`, `hmm_reading`, `predict_ahead_hmm`, `_stay_probs`):

- State: the six diatonic triads (twelve with major/minor of the key ambiguous, if key detection moves server-side later).
- Emission per half bar: `p(weights | chord) ∝ (coverage + floor)^alpha`, the same coverage as today, computed on notes shifted by the *measured* detection latency instead of a tick offset.
- Transition per half bar: `stay(bar_line)` on the diagonal, `(1 - stay) * T_genre[i][j]` elsewhere, with `T` from `transitions.json` or the hand table.
- Forward filtering (not Viterbi) at every tick gives a posterior over the current chord; the chord for the window k downbeats ahead is `posterior @ T^k` (only bar-line transitions), argmax. Second-order effects can be had by expanding the state to (prev, cur) pairs, which is what `learned_second` does by hand.
- What disappears: `rejected()` (evidence accumulates in the posterior; a held chord keeps its mass), the four `decide` rules (the posterior is the blend), the harmonizer's hysteresis (the stay probability), `recent_sources`, and `hmm_reading`. What stays: `fit_transitions.py`, `pitch_class_weights`, `diatonic_triads`, `chord_name`.
- Bench it on the same four scenarios *and* on the two real clips in `bench/streammuse/out/*.mid` and the `TestLiveReplay` sequence; report both, and stop tuning constants on the synthetic set.

License. Chordonomicon is CC BY-NC 4.0 (`fit_transitions.py:6, 29`). `data/transitions.json` is a derived work of the corpus; it is committed to a public repo and served from a service behind `duetai.art`. For a hackathon demo this is within "non-commercial". The moment duet.ai carries any paid tier, the fitted matrices cannot ship, and switching `PREDICTOR` to `'table'` does not fix that while the file is in the repo and the code path is live. Either keep the hand table only (and delete the JSON), or refit on a permissively licensed source (e.g. the chord annotations in POP909 or the Isophonics/McGill Billboard sets have their own terms; check before use), or get written permission from the Chordonomicon authors. Attribution is present (`transitions.json.source`, README), so the BY half is satisfied.

## 3. Timing

Protocol (`amtEngine.ts:212-232, 413-425`; `server.py:237-239`): at each bar the clock fires `cue(bar, 4*bar)`; a `setTimeout` fires the second cue at `4*bar + 2`. Each cue is `{type:'tick', beat, cueId, latestCaptureTimeSec}` preceded by a `set` flush and a `notes` flush. The server answers with a `plan` for `[beat+2, beat+4)` and a `status`.

Budget at 90 bpm (beat 667 ms): the plan's first note is due 2 beats = 1333 ms after the cue. Measured cue-to-plan through the relay: 278 ms mean / 378 ms p95 with ~104 ms server time (`bench/streammuse/REPORT.md`, AMT rows), i.e. ~170 ms for laptop -> Cloudflare -> RunPod proxy -> nginx -> uvicorn and back, which matches the ~165 ms of ~220 ms figure quoted for this review. Smoke thresholds are mean <= 400, p95 <= 600 (`services/smoke.mjs:273-274`). So the steady state has ~1 s of slack at 90 bpm, and none of it is spent on purpose.

Where a second can hide:

1. `GENERATION_BUDGET = 0.8 * window` (`server.py:71, 303`) is not tempo-aware and does not subtract the hop. At 90 bpm the deadline is 1067 ms; add 170 ms hop and 20 ms `MIN_LEAD_SEC` (`amtEngine.ts:27`) and the plan's first note lands 1257 ms after the cue against a 1333 ms window: 76 ms of margin. At 120 bpm the window is 1000 ms, the deadline 800 ms, the margin is 10 ms; at 140 bpm it is negative. A deadline hit is logged as "(hit generation budget)" and otherwise silent; the client counts the late notes in `tooLate` (`amtEngine.ts:132, 444-447`) and never reports the count. Fix: `deadline = window_s - measured_rtt - 150 ms`, and put `tooLate` in `onStatus`.
2. The half-bar cue is a `setTimeout` (`amtEngine.ts:220-224`). Browsers clamp timers in background tabs to >= 1 s; a demo laptop with the tab hidden (screen share, alt-tab) cues the second half of every bar late by up to a second. The bar cue comes from `ToneClock.onBar`, which is Transport-driven and not clamped. Both cues should come from the Transport.
3. `LatestPlanner` deep-copies the session on every cue (`live_session.py:701`, `clone_session` at 633). The copy includes the token list (up to 16 beats of melody + accompaniment, hundreds of ints: cheap) and `PerformanceHistory.records` (a dict per note with the whole client note dict: still cheap). Measured `queueLatencyMs` / `requestAgeMs` are sent in `status` (`live_session.py:711, 721`) and the client discards them (`amtEngine.ts:564` reads only `latencyMs`). Surface them before assuming they are small.
4. A single `inference_lock` across all connections (`server.py:80, 401, 424`). Two performers on one pod serialise; the second's cue waits for the first's generation. `LatestPlanner` then drops superseded cues (newest wins, `live_session.py:665-667`), so the failure mode is a skipped half bar, i.e. silence, not lateness.
5. Model load happens on the first WebSocket, under the lock (`server.py:401-407`), not at process start as the module docstring claims (`server.py:4`). The first user after a restart waits ~3.6 s (log: 23:34:08.660 to 23:34:12.261) and the client's 8 s timeout (`amtEngine.ts:423`) is the only thing between that and a fallback to Patterns.
6. Relay keepalive: the Worker sends `{"type":"ping"}` upstream every 30 s (`relay/src/index.ts:427`), the server answers `pong` (`server.py:434-435`), and `pipe(upstream, server)` forwards the `pong` to the browser (`index.ts:323`), which ignores it silently (`amtEngine.ts:544-588` has no branch for it). Harmless, but it is one more frame per 30 s on a socket that the browser reads on the main thread. The RunPod proxy idle limit is 100 s (`services/README.md`), nginx `proxy_read_timeout 3600s` (`pod-bootstrap.sh:91`).
7. `NOTE_BATCH_MS = 100` (`amtEngine.ts:22`) is bypassed by `cue()` (`amtEngine.ts:418`), so it does not delay the plan. It does delay the harmonizer's view of mid-half-bar notes by up to 100 ms, on top of the detector's own latency; those notes only matter for the *next* cue anyway.
8. Tempo change (`amtEngine.ts:377-384`): `setBpm` closes the socket and opens a new one. New session, empty history, `listen_beats` 8 gate again (`server.py:277`): every tempo step of >= 2 bpm (`amtEngine.ts:68`, `main.ts:544`) costs a reconnect plus two bars of silence. In follow mode a singer who drifts gets 4 s of silence per drift. Worse: the relay's per-IP upgrade cap is 6 per minute (`index.ts:234-235`); the seventh tempo step in a minute gets 429 and the client falls back to Patterns for the rest of the set.

## 4. Overcomplication and duplication

`server.py` (529 lines) carries: the model loader, an unused `ChordInference` (`server.py:104-120`, no caller anywhere), the session state machine, the generation loop, the plan/status wire format, the WebSocket endpoint, and a 60-line CLI bench (`run_bench`, `server.py:454-512`) that drives the old `bar` path. Splitting the generation loop and the wire format out would leave a ~150-line server.

Dead code in the service (defined, tested, never called from `server.py`): `early_entry_plan`, `fill_silent_window`, `voice_chord`, `Arranger.failure_fallback` (`arrangement.py:70-167, 236-242`), `ChordInference.root_below`. Commit `006c39e` ("never commit an empty window") introduced the fill and a later refactor removed the calls; the tests (`test_arrangement.py`, `test_arranger.py`) keep them alive. `services/README.md` still documents the fill ("bar 1 already gets a key-only fallback plan") and `services/amt/README.md` still documents `ChordInference` ("Bass is the inferred chord root ... mode of accompaniment pitch classes"). Both are wrong today: bass is whatever GM program 32-39/42 the model wrote, mapped by `role_for_instrument`.

State kept on both sides:

- chord: client detects it (`main.ts:222`), sends it in every `set` (`amtEngine.ts:328`), server ignores it after four notes, sends its own back, client overwrites its own store with it (`main.ts:347-353`) and then sends it back again in the next `set`. One field, three writers.
- section: client `SongForm` keeps ticking "so the fallback stays warm" (`main.ts:158, 219`), server `form.py` is the same code ported, `planFreshness` arbitrates per bar. A deliberate choice per the one-brain spec; it still means two state machines and a freshness comparator to reconcile them.
- key and tempo: sent at `start`, tempo change = reconnect (above); key change is a `set` the brain accepts mid-song (`brain.py:329-330`) while the token history stays.
- `intensity` / `silenceBeats` are computed on the client from the same notes the server already has (`amtEngine.ts:335, 338`) and shipped over so `form.py` can tick. The server could compute both from `PerformanceHistory`.

Protocol fields nobody reads: `status.tokensPerSec`, `status.queueLatencyMs`, `status.requestAgeMs` (client reads `latencyMs` only); `plan.cueId` (client sends and never checks it against the reply; only `latestCaptureTimeSec` is used, `amtEngine.ts:579`); `ready.performanceEvents` is read (`amtEngine.ts:557`), `ready.tick` is read; `set.instruments` (server: "accepted, no-op"); `notes[].vel`, `.source`, `.confidence` (server keeps beat/dur/pitch/id/held only, `performance_history.py:849-867`); `plan.section` on the listening/idle plans is sent but the client only acts on `ending`.

Back-compat shims that can go once the deployed client is the only client: the `bar` cue and `generate_next_bar_plan` (`server.py:233-235, 391-393`), `PLAN_LOOKAHEAD_BEATS = 4.0` default (`server.py:126`; the client always sends 2), `set.chord` + `CLIENT_CHORD_MAX_NOTES`, the `ready` capability flags (the client can assume tick+performance), and the `SAMPLER` env switch with its second `tokens_generated` formula (`server.py:65-67, 346-352`).

Markdown: `INTEGRATION.md` and `INTEGRATION_FORM.md` are pre-implementation wiring notes whose every step has landed (commit `9cd129d`); `INTEGRATION.md:39` still instructs to drop a line that is already gone. `CREATIVITY_BENCH.md`'s "Proposed follow-up for server.py (not implemented here)" is implemented (`brain.py:277-292`). `HARMONY_BENCH.md` and `README.md` name the wrong default predictor. Keep the two bench result files, regenerate them, delete the two INTEGRATION files.

Bench scripts: `bench_harmony.py` (brain, synthetic arpeggios) and `bench_creativity.py` (filter only, random note clouds, no model) do not overlap with each other. The real duplication is in how many ways the *service* is driven: `server.py --bench` (bar path, synthetic melody, in-process), `bench/streammuse/tools/amt_client.py` (bar path, MIDI in, websockets), `bench/streammuse/tools/tick_latency.mjs` (tick path, relay), and `services/smoke.mjs` (wraps the last). Three of the four use the deprecated `bar` cue or a private clip; only `tick_latency.mjs` exercises the deployed protocol. Keep `tick_latency.mjs` + `smoke.mjs`, retire the other two.

Pod scripts: `pod-bootstrap.sh:27` clones `github.com/w1ne/duet.ai`; `wrangler.toml:512` and the relay's collaborator check use `w1ne/backline`. Python deps on the pod are unpinned (`pod-bootstrap.sh:59-60`: `transformers`, `torch`, git HEAD of `anticipation`), which is how the log's `token_out_embeddings UNEXPECTED` load report and the safetensors-convert 503 appeared. `services/amt/requirements.txt` exists but bootstrap does not use it.

## 5. Robustness

- Model timeout: server side, `deadline_s` ends the sampling loop and the partial window is committed (`cached.py:794`). A stuck CUDA call is not interruptible (`live_session.py:702-708` explicitly awaits it) and holds the global lock; every connection then hangs. `/health` keeps returning 200 (`server.py:85-87`), so `watchdog.sh` never restarts it. Client side: 8 s `responseTimer` (`amtEngine.ts:420-424`) -> `onError` -> `armFallback.trigger` (`main.ts:394-411`) -> Patterns. The wrapper installed by `armFallback` is never removed after `settle()`, so *any* later AMT error, at any point in the set, switches the band to Patterns permanently. There is no path back to AMT without the user re-picking the engine.
- Pod restart mid-session: the socket closes, `onError('AMT: closed')` (`amtEngine.ts:207-210`) -> Patterns as above. The status label says "Reconnecting" (`main.ts:333`); nothing reconnects. `amtEngine.ts` has no retry, no backoff, and `stop()`+`start()` is the only way to get a new socket.
- WebSocket drop without close (network blip): the client has no ping and no read timeout; it notices only when the next cue's 8 s timer fires, then falls back. The relay's 30 s keepalive is upstream-only.
- Thirty seconds of silence: the `not self.human_notes` gate only applies before the first note (`server.py:277`). After that the model keeps generating against a context that, after 16 beats, holds only its own committed notes; the harmonizer returns `held or tonic` (`harmony.py:136`), `decide` returns the held chord (`predict.py:636`), so the band vamps on the last chord. `form.py` ends the song after `silenceBeats >= 16` (`form.py:430, 474`) if the client keeps sending `silenceBeats` in `set`; at 90 bpm that is 10.7 s of silence, then `ended` and empty plans until the next note (`brain.py:343-347`). Reasonable behaviour, entirely dependent on a client-computed field.
- Tempo change: see 3.8; a reconnect per step and a rate-limited relay.
- Health is not readiness: `/health` returns 200 with `status: "loading"` before any model exists (`server.py:87`), and the relay counts any `res.ok` as `amt: true` (`index.ts:450-451`). A pod whose HF download fails reports healthy forever while every connection dies at `load_model`. The watchdog (`watchdog.sh:229-236`) and `deploy-amt.sh:168` both key on that flag. Only `smoke.mjs`, run by hand, opens a real session.
- Watchdog scope: every 5 min, restarts the tmux session, appends a line to `~/backline-watchdog.log`, no notification. It runs from whichever machine has the crontab; nothing in the repo says which.
- Smoke coverage (`services/smoke.mjs`): health flags, two 8-bar clips at 90 bpm, lookahead 2, assertions on empty plans, cue-to-plan mean/p95, arpeggio chord accuracy >= 40%, and that `groove` appears. Not covered: the listen phase length, a `set` mid-clip, a second concurrent session, the `bar` compat path, reconnect after a server restart, any tempo other than 90, muted roles, and `tooLate` on the client side (the smoke has no client clock).
- `test_session_policy.py` re-executes the production `Session` class from `server.py`'s AST with stand-ins (`test_session_policy.py:36-53`). Clever, and brittle: any new module-level name used inside `Session` breaks the test at import, and the stand-in `Committer` never trims, so monophony is untested there.
- Tests otherwise: 147 + 14 pass locally without torch (`python3 -m pytest` in `services/amt`), relay 31 tests per `DEPLOYED.md`.
